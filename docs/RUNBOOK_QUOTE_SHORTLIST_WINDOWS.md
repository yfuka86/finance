# Windows運用手順 — 気配プリスクリーン K=50 の実測

作成: 2026-08-03。Windows本番VPS側で回す作業の手順書。
研究側の根拠は `docs/PREREGISTER_QUOTE_SHORTLIST.md`、結果は `data/jp_quote_shortlist/summary.json`。

## 0. これは何を確かめる作業か

`ensemble_core` は**シミュレーションでは動く**（単元OOS24+ Sharpe 3.43、`verify_baseline.py`
4/4 PASSで再現確認済み）。動かないのは**気配の取得経路**だけ。

- kabu の `/board` は1銘柄1リクエストで**実測 ~9.5銘柄/秒**。
- 本番ユニバース467銘柄だと**49〜66秒**かかる → 最初に読んだ銘柄と最後の銘柄で
  **気配が1分ずれる**＝バラバラの時点で観測した横断面になる。
- 2026-07-31 の「気配は寄値を予測しない」という実測は、**この66秒スメアと分離できていない**。

今回、**前日確定データだけで候補を50銘柄に絞れば約5秒で撮れる**ことが分かった
（Sharpe は 3.43 → 1.69 に落ちるが基準1.0は超える）。スメアが1/12になるので、
**気配の予測力をはじめて正しく測れる**。

**この作業は「気配が使えるか」を測るためのもの。実弾投入ではない。発注は一切しない。**

## 1. 事前準備（初回のみ）

```powershell
cd C:\path\to\finance
git pull
```

kabuステーションは**夜間セッション切れで毎朝ログインが必要**。自動ログイン設定を確認する
（未設定だと401で不発になる。2026-07-29に実障害あり）。

タスクスケジューラの実行は stdout が cp932 なので **`PYTHONUTF8=1` を必ず設定**する
（¥や絵文字の print で UnicodeEncodeError クラッシュする）。

## 2. 毎朝の実行（平日 08:47 起動）

既存の quotesnap タスクの**コマンドを差し替えるだけ**。既定で50銘柄になる。

```powershell
$env:PYTHONUTF8=1
python -m trading.jp_intraday.live.run_live quotesnap
```

- `--shortlist 50` が既定。`--shortlist 0` で従来どおり全銘柄（比較したい日だけ）。
- 08:50 / 08:55 / 08:59 の3時点を記録する。
- **取得開始のリードは銘柄数から自動計算**される（50銘柄なら目標時刻の約10秒前、
  467銘柄なら約54秒前）。固定70秒だった旧実装のままだと、50銘柄でも「70秒前の気配」を
  撮ってしまい絞り込んだ意味が消えるので、ここは修正済み。
- 出力: `data/live_reports/quotesnap_YYYY-MM-DD.jsonl`
- 返り値の `n_symbols` と `lead_seconds` を毎日確認する（50 と 10.3 になっていること）。

**発注は行わない（read-only）。** entry/exit タスクとは独立。

## 3. どれだけ貯めるか

**最低20営業日、できれば40営業日。** 1朝あたり 50銘柄 × 3時点 = 150ペア。
20営業日で3,000ペア、40営業日で6,000ペア。

途中で `--shortlist` を変えないこと（変えると母集団が変わって比較できなくなる）。

## 4. 判定（データが貯まってから1回だけ）

```powershell
$env:PYTHONUTF8=1
python scripts\analyze_quotesnap.py --book
```

**出すのは「建玉一致率」**（08:50の気配で選ぶ上位/下位8本 vs 実寄値で選ぶ8本の一致率）。
これを2026-07-31に事前登録した対応表に当てる:

| 建玉一致率 | OOS24+ Sharpe 目安 | 判定 |
|---|---:|---|
| 100%（歪みなし） | 3.04 | — |
| **≥75%** | 2.45以上 | **GO** |
| **50〜75%** | 2.2前後 | **減額して開始（¥5M）** |
| **<50%** | 1.4以下 | **NO-GO** |

※この対応表は全銘柄版（Sharpe 3.04基準）で作ったもの。K=50版は素の Sharpe が 1.69 なので、
**一致率から読む「維持率」を 1.69 に掛けて評価する**こと。例: 一致率75% → 1.69×0.81 ≒ 1.37。

**判定に使ってよい量・使ってはいけない量**（2026-07-31確定・変更しない）:

- 使う: **λ**（圧縮率）・**R²**（系統かランダムかの判別子）・**σ_ε**・**建玉一致率**
- **使わない**: 順位相関（±3%クリップは順位相関1.000でも一致率12%）
- **λ単独で判断しない**（一様圧縮は一致率100%＝完全に無害）

## 5. 結果の扱い

- 一致率が出たら `docs/PREREGISTER_QUOTE_SHORTLIST.md` に追記し、
  `research_registry.py` 経由で研究台帳（`--server.port 8502`）に反映される。
- **GO判定が出ても、実弾投入はユーザー承認が必要。** 本番発注に関わる変更は
  マージ/デプロイ前に必ず確認を取る規約。
- NO-GO なら気配経路は throughput 側からも閉じたと確定できる。その場合
  `ensemble_core` は正式に断念し、AGENTS の結論セクションを更新する。

## 6. 注意（既知の落とし穴）

- **`/board` は照会銘柄を自動登録し上限50**（51件目から `4002006`）。
  `kabu_client.board()` が**45件ごとに `PUT /unregister/all` を自動で挟む**ので
  K=50 でもそのまま回る。1スナップは 50件＋解除1回＝51リクエスト ≒ 5.4秒で、
  自動計算されるリード10.3秒に収まる。**K を大きくすると解除の回数が増えて
  同時性が落ちる**（そこが今回の肝なので安易に増やさないこと）。
- 参照系のレート制限は **10req/s**、11件目から429。**Session再利用が必須**
  （無いと1req/秒に落ちる）。
- 大引けは **15:30**（15:25からプレ・クロージング）。この作業は寄前だけなので無関係。
- 検証環境(18081)は**板が全null**。板は本番読取が必須
  （`KABU_DATA_ENV=prod` の HybridKabuClient）。

## 7. 数字の留保（重要）

K=50 の Sharpe 1.69 は **1σが±0.99**（OOSが2.5年しかない）。値そのものに精度は無い。
確かなのは方向だけ:

- 逆向きの絞り込み（gap_vol60 昇順）にすると **−0.93** に反転する
- 年別は 2024:1.97 / 2025:1.22 / 2026:2.08 で**全年プラス**
- 独立な指標（amihud20 降順）でも **1.51**
- 最も流動性の高い50銘柄で絞ると **0.03**（＝αは流動性の下位テールに宿る、と整合）

**「1.69が出る」ではなく「1前後は期待できそう」と読むこと。**
